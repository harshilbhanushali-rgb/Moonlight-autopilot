## Open, in the order I would take them

### 1. Input gate — highest value, and the only item validatable without ground truth

4 of 32 in-scope calls are not sales calls, and each got a type, a score and a card:

- single 30-word turn over a 1156s meeting → Discovery / Low
- recording captures only the meeting moving to Zoom → Discovery / Low
- client no-show, two Joveo staff talking to each other → Follow-up Demo / Low
- HelloWork supply negotiation (counterparty is a job board refusing Joveo access) →
  Discovery / **Medium / Risk / 1 coaching gap**

All four are structurally detectable: a word-count floor, no participant on the client's
email domain, a transcript ending in "see you on Zoom". Because the criteria are mechanical
rather than judgement calls, **this needs no labels to validate** — which after today's
findings is the binding constraint on everything else.

Undecided: whether a rejected call gets a distinct `analysis.status` (visibly excluded) or
is skipped at fetch. Prefer the former; the project's pattern is visible status over silent
state. Note the thin-content open decision in CLAUDE.md already argues the word-count floor
sits somewhere under ~300 words.

### 2. Extend R2 to the four untouched rubrics — and how to test it

R2 = give every theme the three-part shape R1 used: **precondition, observable behaviour,
and explicit `Do not report this theme if…` criteria.** Applied to discovery it produced
more good notes at higher precision. **Applied to pricing it failed and was rejected** — so
this is four separate experiments, not one rollout. Do not presell the result.

Targets: `demo` (9 themes, 2 of which have never fired), `follow_up_demo`, `kickoff`,
`technical_integration` — all still `v1-descriptiononly.yaml`.

**Method — this part is not optional.** Gap generation reproduces only 43% of the time, and
two prompt changes in this project were judged after the fact and produced confident wrong
conclusions (8.7, 8.13).

```bash
# same-session control: v1 and the new version in ONE run, two independent nonces
uv run python -m app.services.eval.rubric_version_ab --call-type Demo --labels v1,v2 \
  --theme "<theme being changed>" --verify-all --nonce r1 --out demo_r1.json
uv run python -m app.services.eval.rubric_version_ab --call-type Demo --labels v1,v2 \
  --theme "<theme being changed>" --verify-all --nonce r2 --out demo_r2.json
```

- **`--verify-all` is mandatory here.** Loosened wording raises raw gap counts for free, so
  **the deciding metric is gaps *surviving verification*, never raw counts.**
- **Two runs minimum per arm**, different nonces (the gateway caches on request messages).
- **Fix success criteria in writing before running.** And set them on the outcome, not a
  proxy: in R2 I set "Swim Lanes must fire ≥2 times" and it was the wrong measure — the
  theme ended up producing the *same 3 good notes* from half the firings, which is a win the
  criterion would have scored as a failure.
- **Watch for the pricing failure mode**, which is not obvious: a precondition can strip the
  *good* firings and leave the doubtful ones. `IC-Level Only` did not merely fire less, it
  became less reliable (v2 kept 8/9 and 8/8; the R2 attempt kept 4/5 and 3/6).
- **Reject per rubric.** Rubrics are per-call-type files, so keeping one win without another's
  regression costs nothing.

**Corpus limitation to solve first.** Calls per type: demo 8, follow_up_demo 8,
technical_integration 7, **kickoff 4**. Kick-off is the most tempting target (all three
themes saturate) and the least conclusive at n=4. Fetch more calls before measuring it —
`uv run python -m app.services.fetcher.run --limit N`, no LLM cost.

### 3. Widen Kick-off's gap rubric — small and well evidenced

Kick-off's **scoring** prompt already describes ongoing delivery governance (Goal & KPI
Alignment, Roles/Responsibilities/Governance, Onboarding Timeline & Milestone Review, Mutual
Accountability, Communication Rhythm & Cadence, First Action Item Alignment). Its **gap
rubric** contradicts that: all three themes are pinned to one moment — "Agenda Not
Proactively Set", "Scope Not Locked *Before* Kick-off", "Success Metrics Not Agreed *at
Start*" — so they cannot fire meaningfully on the Nth weekly call, which is why they
saturate at 75–100% and carry no information. Align the rubric with its own scoring
categories. Combine with #2's method.

### 4. Split themes into universal vs stage-specific — biggest lever, still a hypothesis

Of Demo's nine themes only three are demo-specific (`Slide Reading`, `Demo Not Customised`,
`Irrelevant Content Shown`). The other six are true of any sales call. **Demo is the only
rubric that has universal themes and the only one that does not saturate** — the 3-theme
rubrics contain nothing but narrow absence-claims, so a model that must report something
reports those.

Giving every rubric the universal set plus its own specifics would absorb mixed-stage calls
(a discovery/demo call keeps most of what matters whichever label it gets), relieve
saturation, cut the duplication across six rubrics, and reduce what a wrong `call_type`
costs. **Not measured.** Test it the same way as #2.

## Do NOT redo these — all tried and failed, all recorded

- **Verifier reframe** (8.13). Asking the neutral "does this call exhibit theme X?" fixed 0
  labelled gaps and broke 8. The leading question is load-bearing.
- **Verifier prompt hardening** (8.7). 84/86 gaps identical, two flips in opposite
  directions.
- **Theme falsifiability probe** (8.6). 0/25 twice; hypothesis disproven.
- **call_type prompt tuning** (8.16). 6/8 then 8/8 on identical input — unverifiable at this
  sample size. Revisit only with many more labelled calls.
- **A seventh call type.** Ruled out by the user, final. Solve recurring cadence inside the
  six (see #3).
- **Rationale comments inside prompt files.** They are sent to the model verbatim. Keep
  rationale in commit messages until the storage redesign lands.
- **`Ground_Truth_call_type/` as a test set.** It is the six sections of `Call_examples.md`,
  the material the prompt was written from. Floor check only.
